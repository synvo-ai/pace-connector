How an email passes through the privacy connector

The connector is a small Python service that runs inside RSTN's network, next to their email system. It sits between the PaCE mailbox and Synvo's engine. Its job is to make sure that only masked text ever leaves, and that the answer coming back is made readable again on the NTU side.

1. The picture

Three parties are involved. RSTN's system reads the mailbox through Microsoft Graph. The connector, hosted by RSTN, does all the privacy work. Synvo's engine, hosted by Synvo, reads the masked enquiry and recommends what to do. The dashed line is the trust boundary: only masked JSON crosses it.

RSTN's system talks to the connector in plain HTTP inside its own network (POST /v0/messages). The connector talks to the engine over the engine's API (POST /v0/enquiries?mode=sync, with an API key). RSTN's system never calls the engine directly.

2. One email, step by step

The example is examples/graph_with_attachment.json: a reply from a prospective student, as Microsoft Graph returns it, with a payment receipt image attached. Every snippet below is real output from the connector running against the engine on 15 Oct (engine in offline test mode, so its answer text is a fixed sentence).

1

Receive server.py

RSTN's system posts the Graph message as it is, as application/json. A raw .eml works too, as message/rfc822. To have attachments read, RSTN fetches the message with ?$expand=attachments; otherwise the connector only records that there was an attachment.

POST /v0/messages
content-type: application/json

{ "id": "AAMkAExample0002", "conversationId": "AAQkAExampleConversation0001",
  "subject": "Re: Enquiry about Advanced Professional Certificate in Data Science and AI",
  "from": { "emailAddress": { "name": "Tan Mei Ling", "address": "meiling.tan@example.test" } },
  "body": { "contentType": "html", "content": "<div dir=\"ltr\">Dear PaCE team, … <div class=\"gmail_quote\"> …" },
  "attachments": [ { "name": "receipt.png", "contentType": "image/png", "contentBytes": "iVBORw0…" } ] }

The connector then derives the three IDs the engine needs from the Graph message id: a request ID, a correlation ID and an idempotency key, each a fixed prefix plus 32 hex characters. Because they come from the message, sending the same email twice produces the same IDs, and the engine returns its first answer instead of working again.

2

Parse and cut the quoted history graph.py · mime.py

The HTML body becomes plain text. Everything from the first quote block onward is cut: Gmail's gmail_quote, Outlook's divRplyFwdMsg / appendonsend, a <blockquote>, or in plain text an "On … wrote:" line or "-----Original Message-----". The sender, recipients and Graph IDs are kept aside locally and are never sent.

Body as received (shown as text)
Dear PaCE team,
Thank you for the details.
I would like to know more about the funding options for this course. My mobile is +65 9123 4567 if a call is easier. I have attached my payment receipt.
Thanks & Regards,
Tan Mei Ling
On Mon, Oct 12, 2026 … PaCE Enquiries wrote:
Dear Tan Mei Ling, The next intake starts in January 2027. …
Current message kept
Dear PaCE team,

Thank you for the details.

I would like to know more about the funding options for this course. My mobile is +65 9123 4567 if a call is easier. I have attached my payment receipt.

Thanks & Regards,
Tan Mei Ling

Limits are checked here: at most 256 KB per email, 1,000 characters of subject, 40,000 of body and 24 attachments. Anything over a limit is not sent; it goes to manual handling.

3

Read attachments, black out, read again attachments.py

PNG and JPEG images are read with on-device OCR on the CPU; the OCR model files ship inside the package, so nothing is downloaded. PDFs use their text layer when there is one, otherwise each page is rendered and read with OCR (up to 10 pages, 8 MB, 12 seconds per attachment). Then:

  • personal details are found in the OCR text and mapped back to their positions on the image;
  • those areas are blacked out in the pixels;
  • the blacked-out image is read again, and if any personal detail can still be read, the attachment is not used (REDACTION_VERIFICATION_FAILED);
  • if the OCR is unsure (too little text, low confidence, non-Latin script), the attachment is not used either.

Only text from an attachment that passed is sent on, and it is masked like the body. Other file types are listed as "attachment present, not read". File names, images and bytes never leave.

[attachment PRIVACY_VERIFIED, OCR]
Payment receipt Paid by: [[PII_PERSON_iAA6IZ2EZLYe_0002]]: [[PII_PHONE_iAA6IZ2EZLYe_0001]] Amount: S$500.00 Reference: PAY-2026-0042
4

Mask personal details privacy.py · masking.py

Two detectors run on every text field (subject, body, attachment text, any thread or earlier issues RSTN supplies):

  • rules for emails, Singapore phone numbers, NRIC/FIN, and application, reference, account and payment numbers with a prefix;
  • name checks: a local English name recogniser (spaCy), plus rules for where names sit (after "Dear", in a sign-off, after "my name is", in a "Name:" field, after "Ms" or "Dr"), for name-shaped words (capitalised words in a row that aren't ordinary English, such as "Mei Xuan Koh"), and the sender's and recipients' own names from the email envelope.

Each value is replaced by a placeholder such as [[PII_PERSON_iAA6IZ2EZLYe_0001]]. The same value gets the same placeholder throughout the email, so the engine can still tell that the phone in the body and the phone on the receipt are the same. The middle part is a per-email code computed from the idempotency key and a secret held only by the connector, so it can't be guessed, but a resend of the same email gets the same placeholders. The map from placeholder to real value stays in the connector's memory for this one request only.

This is the complete request that leaves the NTU side. Running the connector with --show-masked adds it to each answer, so testers can check it themselves.

5

Independent egress check privacy.py: EgressPrivacySentinel

Just before sending, a second checker scans every string in the outgoing JSON. It doesn't use the name recogniser, so a recogniser miss is not automatically a miss here. It looks for anything that still looks like an email, a phone number or an ID number. It also checks for a person's name left in a name position, a name-shaped run of words, the sender's or a recipient's name, or a capitalised word next to a masked name. If it finds one, nothing is sent and the email goes to manual handling with EGRESS_PRIVACY_CHECK_FAILED.

Changed on 15 Oct: the check used to treat any two capitalised words in a row as a possible name, so it blocked most ordinary emails ("Applied Data", "Dear Sir"). On 91 made-up enquiries it now blocks none (was 73), and no name leaves unmasked (was 4 of 122). Names that are ordinary English words and stand alone without a cue ("please ask Hope") can still pass. Measured with benchmarks/egress_rates.py; see benchmarks/README.md.
6

Call the engine client.py

One HTTPS call to the engine with the API key, waiting for the result. If the engine is briefly unavailable or busy (5xx, 429), the connector retries a few times with the same idempotency key, so the engine never runs the same email twice. The engine works only on the masked text. It returns one or more issues, each with a recommended action (ANSWER, CLARIFY, HANDOFF or MANUAL_REVIEW), the owning team, the evidence it used, a draft reply and a verification status, all still containing placeholders.

7

Restore names, locally service.py

The connector puts the real values back into every text field of the result: the reply draft, issue summaries and handoff notes. This uses the in-memory map from step 4, which is then dropped. If the engine shortened a text and cut a placeholder in half, the fragment is removed rather than shown.

From the engine
"summary": "… My mobile is [[PII_PHONE_iAA6IZ2EZLYe_0001]] if a call is easier. …"
Returned to RSTN
"summary": "… My mobile is +65 9123 4567 if a call is easier. …"
8

Answer RSTN's system server.py

Always HTTP 200 once the email has been processed, either COMPLETED or REQUIRES_MANUAL_HANDLING with a reason code. The Graph IDs are echoed back so RSTN can match the answer to the message and conversation.

{
 "schemaVersion": "pace-connector-http-v0",
 "status": "COMPLETED",
 "failure": null,
 "message": { "id": "AAMkAExample0002", "internetMessageId": "<example-002@example.test>", "conversationId": "AAQkAExampleConversation0001" },
 "result": {
   "issues": [ { "issueId": "ISSUE-001", "recommendedAction": "MANUAL_REVIEW", "summary": "…", "owner": null, … } ],
   "verification": { "status": "SAFE_TO_REVIEW", "findings": [] },
   "handoff": [], …
 },
 "reply": { "subject": "Response to your enquiry", "body": "Regarding your payment status, we're unable to confirm this from the information currently available. …" }
}

3. What never leaves the NTU side

ItemWhat happens to it
Sender and recipient names and addressesRead from Graph or headers, kept local, never put in the request.
Graph message, conversation and Internet message IDsKept local and echoed back to RSTN only. The engine gets derived opaque IDs.
Quoted earlier messagesCut before masking and not sent.
Attachment files, file names, imagesRead in memory. Only verified, masked text from them is sent.
Personal details in the textReplaced by placeholders before sending.
The placeholder mapIn memory for one request, then discarded. Never written to disk or logs.
LogsThe HTTP log has the request line and status only, never bodies.

4. When it stops an email

The connector fails closed: when it can't be sure an email is safe to send, it sends nothing and returns REQUIRES_MANUAL_HANDLING with one of these codes, so a person handles the email as today.

CodeMeaning
MALFORMED_EMAIL · BODY_UNAVAILABLENot a valid Graph message or email, or no readable body.
REQUEST_LIMIT_EXCEEDED · ATTACHMENT_LIMIT_EXCEEDEDToo large, or too many attachments.
PRIVACY_SCOPE_UNSUPPORTEDText outside the English/Latin-script scope of phase 1.
MASKING_FAILURE · PRIVACY_DETECTOR_FAILUREMasking could not complete.
EGRESS_PRIVACY_CHECK_FAILEDThe independent check still saw something personal.
ENGINE_UNAVAILABLE · RATE_LIMITEDThe engine could not be reached, or is busy, after retries.
AUTHENTICATION_FAILURE · ENGINE_CONTRACT_REJECTED · IDEMPOTENCY_CONFLICTSetup problems: wrong key, version mismatch, or the same key reused for a different email.

An attachment that can't be read safely doesn't stop the email. It is sent as "attachment present, not read", and the engine takes that into account.

5. Where each step lives in the code

FileRole
server.pyHTTP mode for RSTN's system: POST /v0/messages, GET /v0/health, ID derivation, optional x-api-key.
service.pyMimePrivacyConnector.process(): runs steps 2–7 in order and turns any error into manual handling.
graph.pyMicrosoft Graph message → parsed email (body, quote cut, attachments from contentBytes).
mime.pyRaw .eml → parsed email; HTML to text; quote detection shared with Graph.
attachments.pyPDF text layer, OCR, blackout, verification OCR, limits.
privacy.pyThe masking detector (rules + name recogniser) and the separate egress sentinel.
names.pyName rules shared by masking and the egress check: name positions, name-shaped words, the sender's own name.
masking.pyPlaceholders, per-request map, keyed per-email code, restore.
client.pyEngine call with key, timeout and safe retries.
contracts.py · errors.pyInput/result types, limits and the failure codes above.

6. Running it

# install (Python 3.10–3.12, CPU only)
python3 -m venv .venv && .venv/bin/pip install "pace-connector @ git+https://github.com/synvo-ai/pace-connector.git"
# or, from a checkout of the repo: .venv/bin/pip install -e .

# one email, printed step by step
PYTHONPATH=. .venv/bin/python examples/run_one.py examples/graph_with_attachment.json --api-key <engine key>

# HTTP mode, as RSTN would run it
PACE_ENGINE_API_KEY=<engine key> PACE_CONNECTOR_NONCE_SECRET=<random secret> \
  .venv/bin/python -m pace_connector.server --engine-url <engine URL> --port 8788
curl -s -H 'content-type: application/json' --data-binary @examples/graph_message.json http://127.0.0.1:8788/v0/messages

Settings: PACE_ENGINE_API_KEY (required), PACE_CONNECTOR_NONCE_SECRET (keep it the same across restarts so resends still match), PACE_CONNECTOR_API_KEY (if set, RSTN's system must send it as x-api-key), --host (127.0.0.1 by default), --show-masked (testing only).

7. Known gaps (15 Oct)

  • Programme words: a Title Case programme name with a word the connector doesn't know can be masked as a name, which hides it from the engine. The words of NTU's real programme titles must be added to the connector's public word list before real data.
  • Follow-up emails: the quoted history is cut and not sent, so on a follow-up the engine sees only the newest message. Earlier turns can be passed as a thread and earlier issues in the library call, but the HTTP mode doesn't accept them yet. To agree with RSTN: do they send the earlier messages of a conversation, or should the connector use the quote?
  • Joined OCR lines: attachment text is joined with spaces, so a label after a name can be masked together with it ("Tan Mei Ling Mobile"). This errs on the safe side.
  • Packaging: a wheel with pinned versions and bundled model files for machines without internet; a version check against the engine.
  • Data label: requests are marked SYNTHETIC_TEST_DATA; this must become configurable before any real email is used.
